12. Technical Overview
12.1 Architecture

AgentGuard uses a modular application architecture.

The frontend communicates with a FastAPI backend. The backend performs authentication, authorization, budget enforcement, risk evaluation, and decision-making before interacting with a simulated financial service.

PostgreSQL stores persistent records, while Redis supports shared runtime state and atomic operations where needed.

The actual implementation should ensure that denied requests cannot reach the execution service.

For approval-required requests, the system must create a pending record rather than execute the transaction immediately.

16. API Design

Use REST endpoints with a version prefix:

/api/v1/
16.1 Agent APIs
Method	Endpoint	Purpose
POST	/api/v1/agents	Register agent
GET	/api/v1/agents	List agents
GET	/api/v1/agents/{agent_id}	Get agent details
PATCH	/api/v1/agents/{agent_id}	Update configuration
POST	/api/v1/agents/{agent_id}/revoke	Revoke agent
POST	/api/v1/agents/{agent_id}/activate	Reactivate agent, subject to authorization

Reactivation must be an explicit administrative action and must not override the global emergency stop.

16.2 Permission APIs
Method	Endpoint	Purpose
GET	/api/v1/permissions	List available permissions
GET	/api/v1/agents/{agent_id}/permissions	View agent permissions
PUT	/api/v1/agents/{agent_id}/permissions	Replace assigned permissions
16.3 Transaction APIs
Method	Endpoint	Purpose
POST	/api/v1/authorize	Evaluate a protected action
POST	/api/v1/transactions	Submit a transaction for governance and execution
GET	/api/v1/transactions	List transactions
GET	/api/v1/transactions/{transaction_id}	View transaction details

The authorization endpoint should not execute a transaction merely because it returns ALLOW. Execution should be handled by a controlled orchestration flow that prevents the agent from changing the transaction after authorization.

16.4 Budget APIs
Method	Endpoint	Purpose

CREATE TABLE transactions (

    currency CHAR(3) NOT NULL,
    recipient_id VARCHAR(150),

CREATE TABLE audit_events (
    id UUID PRIMARY KEY,
    event_type VARCHAR(100) NOT NULL,
    agent_id UUID,
    transaction_id UUID,
    action VARCHAR(100),
    decision VARCHAR(30),
    reason TEXT,
    metadata JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
Database Considerations
Add indexes for frequently filtered fields.
Use database migrations for schema changes.
Keep audit records separate from mutable agent configuration.
Restrict audit modification permissions.
Never store API secrets in transaction metadata.
Use database transactions for changes that must be atomic.

The audit table is designed for application-level append-only behavior. Stronger tamper evidence can be added later through restricted database roles, external log storage, or cryptographic chaining.

19. Redis Design

Redis supports runtime state that needs fast access or atomic operations.

Emergency Stop
agentguard:global_stop

Possible value:

STOPPED
RUNNING
Agent Revocation
agentguard:revoked:{agent_id}
Budget Counter
agentguard:budget:{agent_id}:{date}
Rate Limiting
agentguard:rate:{agent_id}:{window}
Important implementation rules
PostgreSQL stores persistent configuration and historical records.
Redis stores fast-changing operational state and counters.
Security-critical state must not silently fall back to an unsafe default.
If the emergency state cannot be verified, protected actions must be denied.
Budget consumption must use atomic operations or database transactions.

A Redis counter by itself is not sufficient to implement a complete financial transaction lifecycle. The implementation must define how reservations, successful executions, failures, and retries affect budget usage.

20. AI Risk Engine — Technical Design
20.1 Purpose

The risk engine evaluates contextual information and provides a risk score and explanation to the governance decision engine.

It does not independently authorize financial operations.

20.2 Initial MVP Approach

Start with a deterministic, explainable risk-scoring module.

This avoids dependence on paid model APIs and provides predictable behavior during the demo.

Possible features:

Feature	Example
Amount deviation	Transaction is much larger than the agent's usual amount.
Transaction frequency	Agent has submitted an unusual number of requests.
Recipient novelty	Recipient has not been seen before.
Budget utilization	Transaction consumes a large portion of the remaining budget.
Failed requests	Agent has recently generated multiple denied requests.
Transaction timing	Request occurs outside the expected operating period.

These are candidate signals, not automatically reliable fraud indicators. The MVP should use a documented, configurable scoring rule and demonstrate how each signal contributes to the result.

20.3 Risk Scoring Interface
def evaluate_risk(transaction, agent_context):
    """
    Evaluate transaction context.

    Returns:
        risk_score: integer from 0 to 100
        risk_level: LOW, MEDIUM, HIGH, or CRITICAL
        reasons: list of explanation strings
    """

Illustrative response:

{
  "risk_score": 78,
  "risk_level": "HIGH",
  "reasons": [
    "Recipient is new",
    "Transaction amount is unusually high",
    "Agent has submitted frequent requests"
  ]
}
20.4 Decision Engine

Conceptually:

def evaluate_request(request, agent):
    validate_request(request)

    authenticate_agent(agent)

    if emergency_stop_is_active():
        return deny("Emergency stop active")

    if agent_is_revoked(agent):
        return deny("Agent revoked")

    if not permission_is_granted(agent, request.action):
        return deny("Permission missing")

    if not budget_is_available(agent, request.amount):
        return deny("Budget exceeded")

    risk = evaluate_risk(request, agent)

    if risk.requires_denial:
        return deny(risk.reason)

    if risk.requires_approval:
        return require_human_approval(risk.reason)

    return allow(risk.reason)

This is illustrative pseudocode, not production-ready implementation.

The budget check and reservation must be concurrency-safe. Before execution, the system should revalidate any security conditions that could have changed since the original decision.

21. Security Requirements

Security is central to AgentGuard because its purpose is to govern potentially sensitive financial actions.

21.1 Agent Authentication

Each agent must authenticate using a server-validated credential.

Possible MVP approach:

Issue a unique agent API key.
Store only a secure hash of the key where feasible.
Authenticate every protected request.
Support key rotation or revocation.
Never expose agent secrets in frontend code or logs.

For production integrations, short-lived signed credentials or stronger workload identity mechanisms may be appropriate.

21.2 Administrator Authentication

Administrative endpoints require authenticated and authorized operator access.

The emergency stop, agent revocation, budget changes, permission changes, and release operation must not be publicly accessible.

21.3 Server-Side Authorization

The backend must load permissions from trusted server-side storage.

The agent must not be allowed to send its own permissions or risk classification as trusted facts.

21.4 Fail-Closed Behavior

If a mandatory governance check cannot be completed:

Policy check unavailable
        |
        v
Protected action denied

The system must not treat an infrastructure failure as authorization to proceed.

21.5 Transaction Integrity

The transaction that is executed must be the same transaction that was evaluated.

Use a transaction ID, immutable request snapshot, and idempotency key to prevent modification and accidental duplicate execution.

21.6 Audit Security

Audit records must not contain credentials, authentication tokens, or unnecessary sensitive financial information.

The normal application workflow should not allow historical audit records to be edited or deleted.

22. Budget Race Conditions

Budget enforcement must remain correct when multiple requests arrive simultaneously.

Example:

Remaining budget = ₹10,000

Request A = ₹7,000
Request B = ₹7,000

A naive implementation might allow both requests to read the same remaining budget and approve ₹14,000 of spending.

That is incorrect.

Required behavior

The system must reserve or consume the available budget atomically.

Possible implementations include:

A Redis Lua script that checks and updates the budget counter atomically.
A PostgreSQL transaction with appropriate row locking.
Another concurrency-safe reservation mechanism.

The design must also handle failed execution and retries so that reservations are released or finalized consistently.

23. Financial Execution Simulator

The MVP should use a simulated financial service.

Responsibilities
Accept execution requests from the trusted backend.
Validate the execution request.
Return a transaction ID.
Simulate success or failure.
Record the execution outcome.
Prevent accidental duplicate execution through idempotency.
Example
{
  "transaction_id": "txn-1001",
  "amount": 5000,
  "currency": "INR",
  "status": "SUCCESS"
}

The simulator should never report a transaction as successful unless its simulated execution actually succeeds.

This approach demonstrates governance behavior without requiring real banking credentials or financial integrations.

32. Final Architecture Decision

For the hackathon, I recommend keeping the implementation to one modular FastAPI backend, one React frontend, PostgreSQL, Redis, and a simulated financial service.

Do not begin with separate microservices for every governance component. Keep the modules separate in code while running them in one backend application.

This approach reduces deployment complexity and makes the security flow easier to test and demonstrate.

The critical request pipeline remains:

Agent → Authentication → Emergency/Revocation Checks → Permissions → Budget → AI Risk → Decision → Execution Simulator → Audit Log → Dashboard

33. Final Project Summary
Product Summary

AgentGuard is a governance platform for autonomous financial agents that enforces least-privilege access, spending limits, contextual risk assessment, real-time revocation, emergency shutdown, and comprehensive audit logging.

Technical Summary

AgentGuard uses React and TypeScript for the operator dashboard, FastAPI and Python for the governance engine, PostgreSQL for persistent records, Redis for runtime state and atomic budget operations, and a simulated financial service for safe transaction execution.

What Makes the Project Valuable?

Its primary differentiator is the combination of deterministic security enforcement and AI-assisted risk assessment in one centralized governance workflow.

AI evaluates contextual risk, while the governance engine remains responsible for enforcing permissions, budgets, revocation, and emergency controls.

Final Hackathon Priority
